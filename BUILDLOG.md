The process, in order. Per step: what I did, what went wrong, what I learned. Raw material for the presentation.

## Trade-offs

Choices where I knowingly gave something up. Each one: the simpler option, the risk it carried, what I chose and why.

### Quotes and figures from exactly the same orders
- **The question:** a why-answer shows a figure ("late orders score 2.0") next to customer quotes. How sure must I be that the quotes come from the same orders as the figure?
- **Simpler option:** let Claude search reviews on its own, and put a label on the quotes ("reviews from late orders"). Little code, easy to explain. Risk: small, but real. A quote from an on-time order could sit next to a late-order figure, and the label would make it look correct.
- **Chosen:** one population. Claude writes one SQL that picks the orders; code wraps it into fixed views, and both the figures and the review search may only read those views. Comparisons carry a cohort label, so each quote is shown under its own group.
- **How it grew:** this was not designed in one go. It grew through the Codex plan reviews, and each step closed a real hole: quotes from another group (round 1), filters that could not express every predicate (round 2), a query that counts all orders anyway and double-counted orders (round 3), quotes from one group shown for the other (round 4), a WHERE that narrows the figures but not the quotes (round 5), and later a HAVING that does the same.
- **Why:** the assessors will try to break the bot. "A figure about late orders, a quote from a happy on-time customer" is exactly the kind of confident mistake the brief calls a failure.
- **What it cost:** more guard rules, more to explain, and the unit that built it ran out of context and had to be split (step 25).

### 9. Decision: Jev as gatekeeper

### 11. Decision: clean layer built by one script, with reconciliation (design question 2)

- **Learned:** "how do you know your clean data is complete?" is answered by reconciliation and lineage, two standard data engineering practices.

### 20. Decision: build in units, each in a fresh session
- **Decided:** build the app as a chain of work units, each in a fresh Claude session with its own pass-or-fail check and its own commit, instead of one long build session. The rule: a build with three or more modules plus a front end, or more than six build steps, runs this way. This app has seven back-end modules, a web front end and ten build steps.
- **Why:** one long session keeps filling its context; by the time it reaches the front end and the evals, the start has been summarised away. A unit starts clean with only the plan and a state file, proves itself with a check, and the loop stops when a unit fails instead of building on top of it. The commits per unit show how the app was built.
- **Did:** a first single-session run (setup and the thin path) was stopped and set aside. The build starts again from the same plan, rewritten into units for a new Codex plan review. ### 24. U4: Full clean layer, lineage and embeddings
- **Did:** `pipeline/build_db.py` now writes the whole star schema (ADR 0003): `clean.orders` (buyer location of that order through the raw `customer_id`, timestamps cast, `delivery_days`, `days_vs_promise`, `is_late` only for delivered orders with a delivery date, `review_score` from the kept review, `n_items`, `n_sellers`, `items_value`, `freight_value`, `order_payment_value`, `n_payment_types`, `distance_km` by haversine between the buyer's and the seller's zip prefix with lat/lng averaged per prefix), `clean.order_items` (+ `category` and `category_english`, falling back to the Portuguese name for the 2 categories without a translation), `clean.payments` (one row per payment; payment type is never a column on orders), `clean.reviews` (latest per order, text, `embedding FLOAT[384]`), `clean.customers` (one row per person, location of the latest order, `n_orders`), `clean.sellers`. `pipeline/lineage.yaml` names every raw column with `to` (clean columns) or `dropped` (reason); the build checks that every raw column has an entry and that every target exists.
